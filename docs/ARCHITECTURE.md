## 为什么"手"要进模组

用外部协议驱动一个假玩家，永远差最后一层：挖掘的输入与门（`doItemUse` 里那个
`mouse.isCursorLocked()`）、放方块的 4-tick 限速、玩家碰撞箱压住目标格、界面抢焦点。
这些都不是"协议问题"，是**客户端内部语义**。所以我们把动作原语做进模组，把"决策"留在外面。

## 为什么"脑子"要在外面

- 改一次计划要重启游戏 = 一天只能试十次；改一次 Python = 一年可以试一万次。
- 语音、多人协调、失败归因，全是要秒级迭代的东西。
- 模型（DeepSeek）只做**建议**，规则才是执行者 —— 模型会幻觉，手不会。

## 三个反复踩中的坑（设计就是冲着它们去的）

1. **"接口回 ok" ≠ "世界变了"。**
   放置假成功（空手照发、读帧缓存）、挖掘被原版每 tick 取消、死亡界面 ESC 关不掉。
   ⇒ 每个动作的判据必须是世界状态：格子由 air 变非 air、`breakingProgress` 真的涨、
   `respawnPlayer` 之后 `still_open=false`。
2. **一次失败有很多原因，混成一个布尔就会写出死循环。**
   放置失败分三类：`cooldown`（等 200ms 重试）、`body_blocked`（退半步）、`permanent`（换格）。
   逃跑也一样：**没有可逃的东西就不该报价**（否则 70 分会永久压住"去吃饭"的 55 分）。
3. **自主链之间是竞价，不是"链太多"。**
   用户链 50 / 囤粮 55 / 防御最高 70。要压住只能 `takeControl(true)`（整条 runner 停），
   所以必须配超时看门狗 —— 谁开工，谁负责收尸。

## 目录职责

| 目录 | 是什么 | 不是什么 |
|---|---|---|
| `companion/` | 决策、语音、队伍、任务层 | 不直接碰 `MinecraftClient` |
| `launcher/` | 实例、jar、启动参数、诊断包、UI | 不做游戏内动作 |
| `tools/` | 自检闸、起身体、长跑、发布 | 不参与运行时决策 |
| `java/` | 模组补丁（GPL-3.0） | 不含业务策略 |
| `config/` | 模板（真配置 git 忽略） | 不含密钥 |

## 验收闸

`tools/companion_gate.py` 一条命令跑 32 项，约 45 秒。它刻意包含**必须有牙**的项：
例如"自听闸"会做一次对照组 —— 把静音过滤拆掉后必须**失败**，否则这个闸本身是假的。
